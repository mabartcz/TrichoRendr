How a render happens

TrichoRendr Architecture

Stage 1 · 3D basics

Shapes are triangles, components are shared pointers

Faces become triangles

SketchUp stores a face as a polygon (any number of corners, can be concave). A GPU and a ray tracer only understand triangles, so every face is cut into triangles: a polygon with n corners always gives n − 2. SketchUp does the cutting for us (face.mesh).

Definitions and instances

A component (a tree, a bench) has one definition (its triangles) and many instances, each just a 4 × 4 transform matrix (move, rotate, scale) plus an optional material.

Backend terms: the definition is an Arc<Mesh>; an instance is (Arc<Mesh>, Mat4). The export writes each mesh once; Blender later copies it per instance (“flattening”), like cloning out of the Arc.

Front and back: the winding order

Which side of a triangle is the front comes from the order of its corners: counter-clockwise when you look at the front. SketchUp gives every face a front and a back material. A mirrored instance (scale −1, determinant < 0) reverses the order, so the renderer would show the back material on the front. cycles.py therefore swaps front and back for mirrored copies.

Textures and UVs

A texture is an image. Each triangle corner carries a UV: a 2D coordinate into that image (0..1, repeating beyond). The renderer interpolates UVs across the triangle and reads the pixel there. Front and back can use different images, so every triangle has two UV sets.

Backend terms: UVs are a lookup key per vertex; the texture is the table. A PNG with transparency gives an alpha value per pixel, which is how a flat card becomes a tree shape.

Our export only asks SketchUp for UVs on sides that can carry a texture; plain colours get zeros. That saves a lot of Ruby time on big untextured surfaces.

Stage 2 · Ruby inside SketchUp

Export: walk the model without freezing SketchUp

SketchUp runs all Ruby on its UI thread and its API is not thread-safe. A one-minute export in one go would freeze SketchUp for a minute. So the export runs in a Fiber (a coroutine): it works for 0.1 s, yields, a UI timer resumes it about 30 ms later, and SketchUp stays usable in between.

Backend terms: cooperative multitasking on a single-threaded executor, with Fiber.yield as the .await point and UI.start_timer as the waker. One rule bit us: never yield in the middle of a SketchUp iterator; iterate a copied array instead, because the model can change while we are paused.

The walk is a depth-first stack over groups and components. For each definition seen the first time, it writes the triangles (pos.bin), UVs and material ids. For every instance it writes one 140-byte record with the accumulated transform. Hidden objects and hidden tags are skipped. Textures are written once into a cache folder, named by a hash, and reused across renders.

The export loop, simplified

# exporter.rb (simplified)
stack = [[model.entities, :root, IDENTITY, inherited_mat, no_faceme]]
until stack.empty?
  entities, key, xf, mat, fm = stack.pop
  mesh = mesh_id(key, entities)   # first time: faces -> triangles -> bins
  inst.write(mesh, mat, fm, xf) if mesh
  entities.to_a.each do |e|         # to_a: safe to pause inside
    next unless group_or_component?(e) && visible?(e)
    pause                          # Fiber.yield when the 0.1 s slice is used up
    stack << [e.definition.entities, e.definition,
              xf * e.transformation, e.material || mat, faceme?(e)]
  end
end

Face-me components (2D trees that always turn to the camera) get an index instead of a baked rotation: SketchUp 2024+ reports stale transforms for them, so Blender turns each one to the render camera itself.

Stage 3 · The contract

The job folder is the API

Ruby and Blender never call each other. Ruby writes flat little-endian arrays plus one JSON file; Blender reads them with numpy in one call each. Sizes are from her garden.

// inst.bin: one per placed copy
#[repr(C, packed)]

    mesh: u32,       // which definition (triangle range in scene.json)
    material: i32,   // painted on the instance, used where faces say -1
    faceme: i32,     // -1 or index into scene.json faceme
    xf: [f64; 16],   // 4x4 transform, column-major, inches
}                    // 140 B

Nothing in the bins depends on the camera or the look. That is what makes the export reusable: a new camera angle, sun time or look slider only rewrites the 177 KB scene.json.

Stage 4 · Python inside Blender

Scene rebuild: from flat arrays to a Blender scene

Each render starts a fresh Blender in the background (blender -b --factory-startup), so the scene is rebuilt from the bins every time. Measured on her garden at 900 × 390 px, 16 samples, one pass.

Flatten. For each mesh, numpy multiplies its triangles by every instance matrix at once (einsum), subtracts the camera position and converts inches to meters. Face-me cards get their turn-to-camera rotation first. Mirrored copies swap front and back.

Pair materials. Each triangle has a (front, back) material pair. Each distinct pair becomes one Blender material that switches on “am I seeing the back?”. Packing each pair into one integer made this step 2.8 s faster (a 1-D sort instead of sorting rows).

Build one mesh. All 3.28 M triangles go into a single Blender mesh with bulk foreach_set calls, no per-triangle Python.

Tried and rejected: keeping components as Cycles instances. With 30,000 separate objects the build and BVH got slower: 38.7 s against 19.2 s for the whole run.

Stage 5 · Shaders

Materials: names decide the shader

SketchUp materials are just a colour, an opacity and maybe an image. Blender needs a shader: a small program describing how light bounces off the surface. cycles.py picks one from a few rules. Try a name.

Matching: the name is lowercased and stripped of accents (Unicode NFD minus combining marks), then checked for any word as a substring. She edits the word lists on the Materials tab; they travel in scene.json.

Stage 6 · Cycles on the GPU

Path tracing: averaging random rays

For every pixel, Cycles shoots a ray from the camera, bounces it around the scene and asks how much light arrives. One random ray per pixel is noisy; the pixel value is the average of many samples, so noise falls with the square root of the sample count. Below is a tiny version from above, like a plan: a block on grass, lit by a sun of real angular size and the sky.

Rays and the BVH. Testing a ray against 3.28 M triangles one by one would be hopeless. Cycles first builds a BVH, a tree of nested boxes, so each ray only visits a few dozen. Building it, and uploading textures to the GPU, is the “preparing scene” pause of about 5 s.

Backend terms: the BVH is a spatial B-tree index; a ray query is a range scan that prunes whole subtrees whose box the ray misses. OptiX runs that traversal on the GPU.

Soft shadows. The sun is a disc, not a point. Rays aimed at random points on the disc hit or miss the block, which gives the soft edge. The Shadow softness slider sets the disc size: 0.5° + 0.2° × value, the same formula as in cycles.py.

Denoising. Blender runs OpenImageDenoise, a neural network that also looks at the surface colour and direction per pixel, so it smooths noise without blurring edges. The toggle here is a crude stand-in that only averages pixels of the same surface. With the denoiser, 32 samples look clean.

Passes. A single render first does 4 samples (a preview appears quickly), then the full count. Batch renders skip the preview.

Stage 8 · Processes talking

Progress and cancel through files

Blender prints TR: <status> and TR_PROGRESS <percent> <eta> lines. The launcher sends them to blender.txt; Ruby reads the last of each every 0.5 s and pushes the whole state into the window. Cancel is a file the launcher polls for.

  L->>B: kill (checks every 200 ms)
Stage 9 · When something goes wrong

Errors in plain words, logs to send

She is not a programmer, so a failed render must say what happened and what to do, and leave enough behind for you to find the cause on her PC.

Checked before the export. The launcher exe must exist and Blender must be found and be version 5 or newer. Both are checked before the export, which can take a minute.

Known failures by pattern. When Blender exits with an error, Ruby matches the launcher and Blender output against a short list. The first match gives the message; anything else is “The render failed.” The window shows the two sentences and a details box to copy (versions, render size, triangle count, logs folder, last 3 KB of output).

Stage 11 · Decisions

Why it is built this way

Why Blender, not our own renderer

Her GPU is a GTX 1060 (Pascal). CUDA 13 dropped Pascal, and wgpu has no hardware ray queries on it, so a homemade GPU path tracer was out. Cycles has OptiX for Pascal, a production denoiser, AgX colour and a physical sky. The cost: users install Blender, and the code that drives it is GPL.

Why a Rust launcher

Started from SketchUp's Ruby, blender.exe pops up a console window. The launcher starts it with CREATE_NO_WINDOW, captures its output into blender.txt and kills it when the cancel file appears. It is about 100 lines.

Why files instead of pipes or sockets

Every run leaves a complete, replayable job: rerun Blender on it directly to debug, render look variants from a script, or copy it into a test. Crashes on either side leave nothing half-connected.

Why one flat mesh

Instancing sounds cheaper, but 30,000 Blender objects cost more in Python object creation and in the BVH than copying 2.4 M triangles in numpy.

measured: 19.2 s flat vs 38.7 s instanced

Why Blender turns the 2D trees

SketchUp 2024+ reports stale transforms for “always face camera” components. The export sends the raw transform plus a flag, and Blender rotates each card about its blue axis toward the render camera.

Why the haze uses a denoised depth pass

The mist pass (distance per pixel) is noisy behind cut-out leaves, because the leaf alpha is sampled randomly. Mixed in raw, it gave white specks in hedges. Running it through the denoiser first fixed that.

Why the preview has a Refresh button

SketchUp's write_image redraws the whole model for every picture: about 4 s on her garden at any size, even without smoothing. On big models the preview updates on request instead of freezing SketchUp after every orbit.

measured: 4.0–4.5 s for 600 px, 1000 px and viewport size

Possible next step: keep Blender running

Every render starts Blender and rebuilds the scene (~10 s here). A Blender that stays open between renders could keep the built scene and only change camera, sun and look, making look tweaks and batches much faster. More moving parts, so not done yet.
